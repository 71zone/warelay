# Delivery behavior

How an incoming WhatsApp message becomes a ChatGPT prompt and a WhatsApp reply. The bridge favors avoiding duplicates over guaranteed delivery. Source: [`src/core/bridge.ts`](../../src/core/bridge.ts), [`src/core/state.ts`](../../src/core/state.ts), [`src/adapters/whatsapp/inbound.ts`](../../src/adapters/whatsapp/inbound.ts), [`src/adapters/whatsapp/ingestion.ts`](../../src/adapters/whatsapp/ingestion.ts), [`src/adapters/chatgpt/chatgpt.ts`](../../src/adapters/chatgpt/chatgpt.ts), [`src/adapters/browseros/mcp.ts`](../../src/adapters/browseros/mcp.ts).

## What is forwarded

Only incoming direct text and extended-text messages and photos are forwarded. Groups, statuses, your outgoing messages, history sync, videos and voice notes are not forwarded. History sync can update the saved directory without sending old messages to ChatGPT. Messages sent before the first time this WhatsApp login connected are ignored; see [Messages sent while offline](#messages-sent-while-offline) for the ones sent while warelay was stopped. Only contacts you have enabled are forwarded; see [Terminal dashboard](../reference/terminal.md#enabling-a-contact) and [Conversations](conversations.md).

## Queue and journal

Messages are processed serially. The bridge saves each message ID in a delivery journal before submitting it, so duplicate events are not resent after restart. The journal and sessions live in `state.json` and hold no message or reply bodies ([Local data](../reference/local-data.md)). Replies use the selected ChatGPT web model and the existing conversation's context.

When the contact answers with WhatsApp's reply feature (swipe or long-press, then Reply), the prompt starts with `Replying to this earlier message:` followed by the quoted text as a `>` block (cut at 2000 characters; a quoted photo or voice note appears as `[photo]` or `[voice message]`), then the contact's own text. Without that, the assistant would only see the short answer and not what it refers to.

## Messages sent while offline

A message a contact sent while warelay was not running (crash, quit, `x` restart, sleeping machine, WhatsApp disconnected) is received when the link comes back and relayed in order like any other, once. While connected, warelay saves the time the link was last alive every 30 seconds and when it closes or stops ([`liveness.json`](../reference/local-data.md#what-is-stored)). On the next start it forwards everything WhatsApp delivers that was sent since that time minus a 60-second margin, at most 24 hours back, and logs `Catching up on messages sent while warelay was offline since 09:41.` followed by `Caught up: relayed N messages ...` when backlog was relayed. WhatsApp hands such messages over as `append` upserts instead of `notify`, so both are accepted. A message already in the delivery journal, or delivered twice in one run, is not resent. With no saved time (first run, new QR pairing) only messages from the start onward are forwarded, so pairing never replays history. Disabled contacts, groups, voice notes and the other non-forwarded types are skipped as usual. Source: [`src/adapters/whatsapp/liveness.ts`](../../src/adapters/whatsapp/liveness.ts).

**Unanswered messages.** WhatsApp does not redeliver a message you already read on your phone, and the app keeps no message store, so the offline backlog above can miss it. Every time the link opens (first start, reconnect, `x` restart), once forwarding is active, warelay therefore asks your phone for the latest messages of each enabled contact's chat, one chat at a time, about 5 seconds after the link opens (Baileys on-demand history). A message counts as unanswered when it is incoming, sent in the last 24 hours, newer than the newest message written in that chat from this account (so a manual reply from your phone answers everything before it), of a forwarded type (text or photo), and not already in the delivery journal. Read state does not matter. Chats with no activity for more than 24 hours are not asked, a phone that does not answer within 20 seconds is logged and skipped, and nothing here blocks startup. To keep assistant usage low, at most the newest 10 unanswered messages of a chat are sent, **as one prompt** (texts oldest first, each with its quote, photos attached), so one chat costs one assistant turn. The prompt is recorded in the journal under the newest message's ID, so a failed one is not replayed. Activity shows `Checking <name> for unanswered messages…`, then either `History for <name>: N messages from the phone, M unanswered, forwarding as one prompt.`, `History for <name>: the phone returned no messages.`, `The phone did not return history for <name> (timed out)...` or `Skipping <name>: no activity in the last 24 hours...`. Source: [`src/adapters/whatsapp/unanswered.ts`](../../src/adapters/whatsapp/unanswered.ts).

## Read receipts

After the new prompt appears in its saved ChatGPT conversation, the bridge marks the original WhatsApp message as read. It does not wait for the assistant's response to finish and does not mark failed or unconfirmed submissions as read. This uses WhatsApp's normal read-receipt API and respects your account's read-receipt privacy setting. Receipt delivery runs independently: a slow or failed receipt does not delay the WhatsApp reply. Failures are reported in Activity without resending the prompt.

## Reading the reply

The response reader matches stable user and assistant message IDs within the same completed turn, then extracts only the assistant message body. It does not depend on rendered message counts, which can shrink as ChatGPT virtualizes older turns. ChatGPT also removes a finished turn from the page when it is far from the viewport, which happens to the newest turn in a long conversation (a tab that was just loaded sits at the top). The reader therefore scrolls the conversation to its end after submitting, whenever the submitted turn is missing, and before reading the reply; without that, a long earlier reply made every later reply unreadable. It does not send headings or action labels. Browser readiness alone does not prove response extraction still matches the current ChatGPT UI. Replies longer than 60,000 characters are not sent; read them in the saved ChatGPT conversation.

## Reconnects and uncertain acceptance

A linked WhatsApp device reconnects on its own after network drops, sleep or VPN changes. It retries with backoff that grows to one attempt every 30 seconds and keeps going until the connection returns, so forwarding stays active and resumes without pressing R. The bridge stops retrying only when reconnecting cannot help: the device was logged out, another client replaced this session, or WhatsApp refused the device. Before the first QR pairing completes, it gives up after 8 attempts.

The bridge checks the MCP connection before submitting each prompt and when you press B. If BrowserOS rejects an expired session with HTTP 404, the bridge creates a new MCP session and reuses its recorded tab and group instead of opening a duplicate ChatGPT tab, with at most one recovery attempt per message. If expiry happens after submission, it resumes observation only when the conversation URL is known. An uncertain submission is never automatically repeated.

## Photos and rich replies

**Photos in.** A photo a contact sends (with or without a caption) is downloaded and attached to the ChatGPT prompt; the caption becomes the prompt text. Videos, voice notes, stickers and non-image documents are still ignored. A photo that cannot be downloaded or exceeds 64 MiB is logged and not forwarded, so ChatGPT never answers a half-message. Several photos sent together arrive as separate prompts.

**Replies out.** The bridge reads the finished ChatGPT answer as structured blocks instead of flat text, then renders each block for WhatsApp so it reads well on a phone and copies cleanly:

| ChatGPT content | On WhatsApp |
|---|---|
| Prose, headings, lists, quotes, links | WhatsApp formatting (`*bold*`, `_italic_`, `~strike~`, `- ` lists), split into messages of at most 4000 characters |
| Code block | Its own message holding only the fenced code, so long-press copy gives clean code. Over 12000 characters it is sent as a `snippet.<ext>` document |
| Writing card (a draft email or message in a bordered card with a Copy button) | Its own WhatsApp-formatted message holding only the draft, without the card label, so long-press copy gives the draft alone. An email card arrives as three messages: an italic `_Subject_` label, the subject text alone, and the email body alone. The prose before and after the card stay separate messages, in order |
| Small table (fits a phone: at most 40 characters wide, at most 8 rows) | Its own message with an aligned monospace grid, so long-press copy gives the table. No file |
| Big table (wider than 40 characters, or more than 8 rows) and a bordered card of three or more rows (such as a letter, a title and a description per row) | A native WhatsApp image of the table as ChatGPT drew it, and nothing else: no text version, no CSV. A table too tall for one picture arrives as up to four images, cut between rows. If the picture cannot be taken, it arrives as text instead: one record per row, plus `table.csv` (opens in Excel or Sheets) when it has more than 8 rows |
| Widget (ChatGPT only; an interactive card that is not a table: a bordered box with buttons or icons, such as a numbered step strip or an "Interview practice" flashcard) | A native WhatsApp image of the card as ChatGPT drew it. A card whose picture mostly shows controls (one with buttons, like the flashcard) is followed by its text as a message of its own, so the question can be copied: only the readable text, without the label, the "4 of 4" counter, icons or button names. A step strip arrives as the picture alone. If the picture cannot be taken, the text arrives instead, one line per step (`*Monitor:* Identify KPI gaps and trends.`) with the icon row left out when the lines repeat its labels |
| Generated image or file | Native WhatsApp image or document, in its position in the reply |

Containers the reader does not recognize (an input form, a box of one or two rows) are read as separate lines of text rather than skipped or run together. If extracting the rich content fails, or the blocks kept clearly less text than the reply has (70% of its letters and digits), the plain text of the reply is sent instead and any generated files stay attached, so a finished reply is never lost. Files in transit live in `media/` under the data directory and are deleted after 24 hours.

**Table and widget pictures.** The picture is a screenshot of the table or widget element in the ChatGPT tab, taken through the page's own compositor (the Chrome DevTools `Page.captureScreenshot` call that BrowserOS exposes), at up to double density and 4000 pixels on the longest side. The tab is not raised or focused and no keys are pressed; only its scroll position changes. Before each capture the bridge checks that nothing (ChatGPT's header or composer, for instance) is drawn over the element, and refuses one that its scroll container clips sideways, so a picture never shows an element cut off or covered. Any refusal or browser error is logged and the element is delivered as text, so a failed screenshot never costs the reply. At most four tables, cards or widgets per reply are pictured; later ones are sent as text. The pictures are taken last and from the bottom of the reply upwards, because ChatGPT discards the rendered reply when the page is scrolled to the top of a long answer and back down. A flashcard carousel exposes only its visible slide, and its sample answer exists in the page only after someone presses "Show sample answer", which the bridge never does; so the other slides and the answer reach WhatsApp only if they were already open in the browser.

## Fallback assistants

ChatGPT's usage limit should not leave a contact without answers. Under the Terminal dashboard's **O** key (the Assistants screen, or `state.json`, see [Local data](../reference/local-data.md#state-file-versions)) you switch assistants on or off and set their priority, for example ChatGPT, then Claude, then Gemini, and how many times a send that provably did not leave is retried before the next assistant takes over (default 2). A single assistant, the default, behaves exactly as before. Source: [`src/core/fallback.ts`](../../src/core/fallback.ts), [`src/core/handoff.ts`](../../src/core/handoff.ts), [`src/core/usage-limit.ts`](../../src/core/usage-limit.ts), [`src/adapters/claude/claude.ts`](../../src/adapters/claude/claude.ts), [`src/adapters/gemini/gemini.ts`](../../src/adapters/gemini/gemini.ts).

**Gemini** (gemini.google.com) is a third assistant through the same BrowserOS profile. Its Google account is an option on the Assistants screen: account 0, 1, 2 or 3, the `/u/<N>/` in the address, default 0. Conversation references always carry that path, for example `https://gemini.google.com/u/0/app/<id>`. Before every send the adapter checks that the page opened that account and logs which email is signed in; if Google redirected to another account or to a sign-in page, the message is not sent (that failure is retried, then the next assistant takes over). After you switch the account, a contact's saved Gemini conversation from the old account is left alone and a new chat starts in the new one. Gemini has no projects to assign, so the project picker lists none for it.

- **Per message, the first assistant not marked limited is used.** A provider's page script recognises its usage-limit notice (ChatGPT "You've hit the usage limit... try again after 3:45 PM", Claude "You've reached your usage limit... resets at 3 PM") and the reset time it shows is read in your local time zone (relative "in 2 hours", a clock time, a weekday or a date). The reset time is only understood from English wording; with no time shown, or a notice in another language, the assistant stays out for 30 minutes.
- **Before the prompt was accepted** the same message goes straight to the next assistant, so nothing is lost and nothing is sent twice. The limited assistant is not tried again until its reset time has passed; then the primary is used again on its own. Limited-until times are saved, so a restart keeps them. The dashboard status shows `ChatGPT limited until 3:45 PM`.
- **A send that did not leave** (tab or composer not ready) is retried the configured number of times, then the assistant is set aside for 30 minutes and the next one takes the message. The last assistant is never abandoned: its failures keep retrying as described below.
- **After the prompt was accepted** it is never sent anywhere else. If the limit appears mid-reply, that reply fails as under "After acceptance" below, but the assistant is marked limited so the next message goes to the next one.
- **All assistants limited:** nothing is sent; the contact gets one WhatsApp line naming the soonest reset (for example "ChatGPT and Claude have reached their usage limits or cannot answer right now. Try again after 3:45 PM."), the message is not replayed and the contact stays enabled.
- **Handoff.** Each contact has a conversation on every assistant that served it. When a message goes to an assistant that has not seen the recent turns (a new conversation on a fallback, or the primary again after the fallback answered), its prompt starts with a framed transcript, "Earlier conversation, continue from it", of up to the last 8 turns and 6000 characters from the last 24 hours, then the new message. The transcript comes from a short text log the bridge keeps itself, not from the old page, and is never sent to WhatsApp. A contact whose conversations have all expired, or who has none yet, starts fresh with no transcript.

## Self-healing and errors

The bridge repairs itself rather than waiting for you to press R or re-enable a session.

- **Not yet sent:** if ChatGPT is not ready before the prompt is submitted (BrowserOS down, tab or composer missing, conversation still generating), or WhatsApp is offline when the reply is ready, the same message is retried with backoff up to 30 seconds for up to 30 minutes. Between attempts the bridge reconnects BrowserOS. This is safe because the provider provably never received the message.
- **Slow replies:** the bridge keeps waiting while ChatGPT is generating or the text is changing. It gives up only after 5 minutes without progress or 60 minutes in total, and retries lost BrowserOS connections the whole time.
- **Stopped forwarding:** while the saved running flag is on, a watchdog resumes forwarding whenever it becomes disarmed (BrowserOS unreachable at launch, channel failure, an unexpected bridge error), with backoff from 15 seconds to 5 minutes. A logged-out WhatsApp device still needs a QR scan.
- **After acceptance:** if ChatGPT accepted the prompt but no reply could be read or sent, the prompt is never replayed, because that could duplicate it. The session stays enabled and later messages flow. The answer may still be in the saved ChatGPT conversation. The contact gets one short WhatsApp line saying either that ChatGPT did not return a reply or that it replied but the reply could not be delivered, with the first sentence of the reason and a request to ask again. That notice is sent once, never retried, and not sent when you paused forwarding; if it cannot be sent either, only Activity shows it.
- **Unknown failures before acceptance:** the session pauses, and you inspect both conversations before enabling it again. Interrupted deliveries are quarantined on restart. The bridge cannot promise exactly-once delivery across two remote services.

Pausing prevents any pending WhatsApp reply from being sent but cannot retract a prompt already submitted to ChatGPT. Quitting disarms forwarding and waits for an in-progress browser operation to finish before closing.

Login expiry and verification challenges require manual attention in BrowserOS; the app does not bypass them or switch silently to an API. A usage limit is handled by the fallback assistants above, which are other web assistants driven the same way. Browser automation can break when ChatGPT or Claude change their UI. See [Troubleshooting](../runbooks/troubleshooting.md) and the [motivation and policy notice](motivation.md).

## Identity aliases

WhatsApp can identify one account by both a LID and a phone number. Verified mappings combine those directory entries, recent chats, forwarding settings and delivery IDs under one canonical identity, so the same message is not delivered twice across aliases. The existing ChatGPT conversation is retained; if both aliases already have different ChatGPT conversations, the bridge refuses to discard either silently. Contacts that merely share a name are not merged. Storage: [Local data](../reference/local-data.md#identity-aliases).

## Observability

Activity logs show elapsed times for ChatGPT acceptance, reply readiness and WhatsApp delivery. Dependency console output is routed into the dashboard, and structured objects are redacted to avoid exposing session keys. Message bodies are not logged.
